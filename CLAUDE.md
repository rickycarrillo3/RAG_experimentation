# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`knowledge-base-math` is a math-focused RAG QA system for family use. Goal: performance comparable to Claude/OpenAI, built entirely on free/open-source models and infrastructure (no paid APIs). It is the only active project in this repo — everything else (other RAG experiments: hybrid retrieval, LLM-equations, vision, speech-to-text) was moved to the `archive/experiments` branch when this one outgrew being a side experiment. The `Base RAG explained/` folder holds the numbered `0X_*.md` general RAG concept notes, kept as background reading.

## Commands

All commands run from `knowledge-base-math/`, with the venv active:

```bash
cd knowledge-base-math
source venv/bin/activate
```

```bash
# Install deps
pip install -r requirements.txt

# Extract a PDF to .mmd (Markdown+LaTeX)
python extract.py docs/raw/textbook.pdf
python extract.py docs/raw/textbook.pdf --force-pymupdf   # skip Marker

# Ingest .mmd file(s) into a user's BM25 + Chroma indexes
python ingest.py --user alice docs/extracted/textbook.mmd
python ingest.py --user alice docs/extracted/                # whole directory

# Query from the CLI (hybrid retrieval + LLM)
python query.py --user alice
python query.py --user alice --retrieval-only    # print retrieved chunks, skip LLM
python query.py --user alice --no-bm25           # dense-only (for comparison)
python query.py --user alice --no-dense          # BM25-only (for comparison)

# Evaluate retrieval — the eval harness lives in evaluation/, run from knowledge-base-math/
# (see evaluation/EVALUATION.md for the protocol — read it before trusting numbers)
python evaluation/make_evalset.py --user alice --n 50   # build evaluation/goldset.jsonl, THEN HAND-CLEAN IT
python evaluation/eval.py --user alice --all            # sweep configs: recall@5, recall@pool, MRR, nDCG, latency
python evaluation/eval.py --user alice --all --answers  # also LLM-judge the end-to-end answers (slow)
python evaluation/embed_chunk_sweep.py                  # 3 chunkers × 3 embedders → evaluation/results/sweep_results.json

# Is the generator's self-consistency (majority vote over k samples) worth k× the decode?
# Closed-book, no retrieval — this measures the generator, not the pipeline. Two tiers:
python evaluation/self_consistency.py                   # --baseline (college, 30 Q) — the deciding tier
python evaluation/self_consistency.py --easy            # grade-school regression tier (20 Q)
python evaluation/self_consistency.py --dry-run         # validate the set, generate nothing
python evaluation/verify_reasoning_set.py               # recompute every gold answer with sympy

# Generator bake-off: which model, and is the Python sandbox worth it? (EVALUATION.md §12)
# --model picks the generator; --tir turns on tool-integrated reasoning. Output paths are
# keyed by tier + model + arm, so the arms coexist and --report-only re-scores any of them.
python evaluation/self_consistency.py --model qwen3:8b --tir
python evaluation/self_consistency.py --model qwen3:8b --tools   # native tool calling (arm E)
GEN_MODEL=hf.co/bartowski/Qwen2.5-Math-7B-Instruct-GGUF:Q4_K_M \
  bash evaluation/eval.sh --skip-sweep --self-consistency --tir

# Pre-download all HuggingFace models (embedder + reranker + Marker/surya, ~6GB cold)
python prefetch_models.py
python prefetch_models.py --skip-marker   # query-only; skips the ~3-4GB extraction models

# End-to-end smoke test: ingests docs/extracted/test.mmd for a "test" user, then interactive CLI chat
python test_chat.py
python test_chat.py --retrieval-only

# API service (this is what gets deployed) — http://localhost:8000
# /docs is served only when KBM_API_TOKEN is unset (or KBM_ENABLE_DOCS=1) — see api/settings.py
uvicorn api.main:app --host 0.0.0.0 --port 8000

# Web UI (upload + chat), http://localhost:7860 — an HTTP CLIENT of the API above,
# so the API must be running first. Set KBM_API_TOKEN in both shells if it is set at all.
python app.py
```

Requires [Ollama](https://ollama.com) running locally with the model pulled:
```bash
ollama pull t1c/deepseek-math-7b-rl:Q4
```

The generator is selected by **`KBM_LLM_MODEL`** (default: the tag above) and is no longer
a literal in the source. Naming a model also configures it — `kbm/llm_profiles.py` supplies its
context window, decode budget and whether it may use the Python sandbox:
```bash
KBM_LLM_MODEL=hf.co/bartowski/Qwen2.5-Math-7B-Instruct-GGUF:Q4_K_M uvicorn api.main:app --port 8000
```

**Agent mode.** A model with a `tools` template gets native tool calling instead of TIR:
it can run Python *and* decide to search the family's documents again mid-answer. Selected
by the profile, overridable with `KBM_TOOLS`, and mutually exclusive with `KBM_TIR`.
`GET /healthz` reports the effective arm as `protocol` (`tools` / `tir` / `none`).

```bash
KBM_LLM_MODEL=qwen3:8b uvicorn api.main:app --port 8000   # protocol: tools
KBM_TOOLS=0 KBM_LLM_MODEL=qwen3:8b uvicorn api.main:app   # protocol: tir  (bake-off arm D)
```

Forced onto a model with no tools template, the server logs an error and **downgrades**
rather than failing every answer — `api/deps.py` asks Ollama's `/api/show` at startup
instead of trusting the profile table. See `AGENT.md`.

On a RunPod GPU pod, see `knowledge-base-math/SETUP.md` for one-time setup and `knowledge-base-math/startup.sh` for per-session start (run from inside `knowledge-base-math/`; GPU check → auth warning → starts Ollama if not already running → `python app.py`). `startup.sh --allow-cpu` runs it locally without CUDA.

There is no automated test suite/linter configured — `test_chat.py` is a manual smoke test, not a pytest suite.

## Architecture

Pipeline: PDF → `extract.py` → `.mmd` → `ingest.py` → per-user BM25 + Chroma indexes → `api/` (or `query.py`) → hybrid retrieval + RRF → cross-encoder rerank → LLM answer.

Serving is split: **`api/` is the deployable unit**; `app.py` and the future TypeScript
frontend are both just HTTP clients of it. See `DEPLOYMENT.md` for hosting, cost, and env vars.

- **extract.py** — PDF → `.mmd` (Markdown+LaTeX). Samples the first few pages to decide the extractor: `marker-pdf` for math-heavy PDFs (proper Markdown+LaTeX via the Surya models), falling back to `pymupdf4llm` on Marker failure or for non-math PDFs. Marker downloads its models to the HuggingFace cache on first run (GPU-fast, CPU-slow-but-correct). Output goes to `docs/extracted/`.
  - **⚠️ DO NOT detect math by grepping for LaTeX (`\frac`, `$$`, `\int`, …) in `pymupdf4llm` output — this mistake has been made repeatedly.** `pymupdf4llm` output contains **NO LaTeX whatsoever**; it renders equations as Unicode glyphs (`γ`, `≡`, `∫`, `∂`, sub/superscripts). Any LaTeX-pattern regex over a pymupdf sample matches nothing, so it silently classifies every math PDF as "not math" and routes it to the wrong (pymupdf) extractor. Math detection on a pymupdf sample must key off **Unicode math glyphs** (or a real layout/OCR signal) — never LaTeX tokens. LaTeX only exists downstream, in Marker's output.
- **kbm/chunking.py** — the three splitting strategies (`baseline` = the old `RecursiveCharacterTextSplitter` 400/80; `eqaware` = never split inside `$$…$$`/`$…$`; `eqaware_context` = eqaware plus the sentence before/after each equation) and `assign_chunk_ids`. The equation-blind baseline will cut a `$$…$$` in half; the eqaware variants keep equations atomic (the overlap seed is equation-aware too). Chunk ids are stable within a strategy but **not comparable across strategies** — eval matches by content overlap for that reason.
- **kbm/latex_norm.py** — `normalize_latex(text)` via pylatexenc, rendering LaTeX to readable glyphs/words (`\theta`→`θ`, `\cos`→`cos`, `\frac{a}{b}`→`a/b`). Used **only** to compute embeddings (see `retrieval.NormalizingEmbeddings`); `page_content` stays raw LaTeX so BM25, the reranker, LLM context, and eval overlap-matching all see the original.
- **ingest.py** — chunks `.mmd` files via `chunking.CHUNKERS[--chunker]` (default `baseline`) and builds two indexes per user: a BM25 pickle (`bm25_indexes/user_<name>.pkl`, `{"bm25": BM25Okapi, "chunks": [...]}`) and a Chroma collection (`chroma_db/`, collection `user_<name>`). Index paths are **imported from `kbm/retrieval.py`** (which re-exports them from `kbm/config.py`), not redefined here — a second local copy of those constants would mean ingest writing where retrieval never reads. `--embed-model` / `--normalize-latex` select the embedder via `retrieval.load_embeddings` (no more duplicate model constant); returns build stats for the sweep.
- **kbm/retrieval.py** — **the retrieval pipeline, and the single source of truth for it.** BM25 top-10 + dense top-10 (`BAAI/bge-small-en-v1.5`) merged via Reciprocal Rank Fusion (RRF, k=60); the RRF top-20 candidate pool is rescored by a cross-encoder (`BAAI/bge-reranker-v2-m3`) and the top 5 go to the LLM. Imported by `query.py`, `app.py`, and `eval.py` — change retrieval behaviour here and nowhere else. Tunables live here too (`TOP_K`, `RERANK_TOP_C`, `TOP_N`, `RRF_K`). `load_embeddings(model_name, normalize_latex)` is the one place embedders are built (query and ingest share it, so query normalization always matches the index); `NormalizingEmbeddings` wraps a base embedder to LaTeX-normalize text before encoding while leaving `page_content` raw.
  - `retrieve()` returns the final top-N. `retrieve_detailed()` additionally returns the pre-rerank candidate pool, the full ranked list, and per-stage timings — that's what `eval.py` needs.
  - **`top_k` bounds the candidate pool**: RRF can emit at most `top_k × 2` candidates, so raising `RERANK_TOP_C` above that is a silent no-op. Raise `top_k` too.
- **query.py** — interactive CLI around `kbm/retrieval.py` + DeepSeek-Math generation. `--no-rerank` / `--no-bm25` / `--no-dense` toggle stages for A/B comparison.
- **kbm/tools/sandbox.py** — the only place model-written code is executed, and the thing that makes both tool protocols possible (`kbm/tools/tir.py`'s text blocks and `kbm/tools/agent.py`'s `run_python`; two callers, one gate). `run_python(code)` → an AST allow-list (whitelisted imports; no `open`/`eval`/`exec`/`__import__`/dunder access), then a **separate short-lived process** in its own session and empty temp cwd with a scrubbed environment, under rlimits and a wall-clock group kill. Output is capped at 400 chars. **It never raises** — a refusal, a `SyntaxError`, a timeout and a crash all come back as a short string the model can read and react to, because "your program had a SyntaxError" is something a generator fixes on the next round and an exception in the server is not. **It is a gate, not a jail**: no namespace, no seccomp, no container, and network isolation is a policy check rather than a kernel boundary — see `DEPLOYMENT.md §8` before widening `ALLOWED_IMPORTS` or exposing this beyond the family.
- **kbm/tools/tir.py** — the tool-integrated-reasoning protocol, pure functions only. Qwen2.5-Math's TIR is **not** OpenAI-style function calling: no JSON tool schema, no `<tool_call>` tag, no `bind_tools()`. It is a text protocol — the model writes a ` ```python ` block, generation stops at the stop word `` ```output ``, and the result is spliced back into the same assistant turn. Every constant here is **Qwen's own** (from `QwenLM/Qwen2.5-Math`'s `evaluation/math_eval.py`), because the model was fine-tuned against that exact shape and drifts off-distribution if it is improvised on. `pending_program()` decides "is the model waiting on a tool?" from the *transcript*, never from `done_reason` — with a stop word Ollama reports `"stop"` for both a stop-sequence and a natural EOS, so `done_reason` cannot tell them apart. An **unclosed** ` ```python ` block is deliberately not a tool call: that is a generation cut off at the token cap, and it belongs to the continuation arm.
- **kbm/tools/agent.py** — the **native tool-calling** protocol, pure functions and schemas only, and `kbm/tools/tir.py`'s sibling rather than its replacement. Where TIR is a *text* protocol the model was fine-tuned on, this is OpenAI-style function calling over Ollama's own `tools` field: a JSON schema goes out, a structured `tool_calls` array comes back, and each result returns as a `ToolMessage` in a **new turn** (TIR pauses *inside* a turn; a native call *ends* it — which is why `api/routes.py` grew a `turns` list). Three tools: `search_documents`, `run_python`, `list_documents`. **This is the first time retrieval is reachable from inside generation** — the model can decide the retrieval the server already did was not the one the question needed, rewrite the query, and search again. ⚠️ **No schema has a `user` parameter and none may ever gain one**: isolation here is directory naming, not auth, so a `user` the model can write is a `user` the model can change — and `search_documents` returns text the family *uploaded*, which is a prompt-injection route (`DEPLOYMENT.md §8`). The caller closes `user` over from the request; static dicts rather than `@tool` callables is what makes that structural instead of remembered. See `AGENT.md`.
- **kbm/llm_profiles.py** — window size, decode budget, TIR capability, **native-tools capability** and thinking-mode per generator, matched by substring against the Ollama tag. Exists because those properties belong to the *model* and arrive together: scattering them is how you end up running Qwen with deepseek's 350-token cap and concluding that TIR does not work. Env vars still override. Imports nothing from the repo, so `kbm/config.py` can import it without a cycle.
  - **`tir` and `tools` are both capabilities, and qwen3 has both.** Which protocol a model actually gets is a *policy*, decided in one line in `kbm/config.py` — `TIR_ENABLED = False if TOOLS_ENABLED else …` — downstream of every env var, so no combination can hand a model a `tools` array *and* a ` ```output ` stop word. It would interleave the two mid-answer: unreadable for the student, un-attributable for the eval. Keeping the two fields independent is also what keeps `EVALUATION.md §12`'s arm D (qwen3 + TIR) runnable via `KBM_TOOLS=0`.
- **api/** — the FastAPI service, and **the deployable unit**. Imports the pipeline from `kbm/retrieval.py`; never reimplements it. Loads embeddings/reranker/LLM once at startup.
  - `api/main.py` app + lifespan, `api/routes.py` endpoints, `api/schemas.py` the wire contract (what the TS frontend is generated from), `api/chat.py` prompts + history + provenance, `api/deps.py` model singletons + auth, `api/settings.py` env config.
  - `POST /chat` streams **SSE**: one `sources` frame, then `token` frames, then `done` (carrying `mode`, timings, the telemetry `event_id`, and `truncated`/`continuations`). `POST /upload` returns a job handle polled via `GET /jobs/{id}` — Marker ingest is minutes long. Also `GET /users/{u}/status`, `POST /feedback`, `GET /healthz`.
  - **Job messages are two strings, not one.** `Job.detail` is a plain sentence for the family member who uploaded the file; `Job.diagnostic` carries the exception text, install URLs and stage for the log and for operators (`KBM_SHOW_DIAGNOSTICS=1` shows it in the UI). Never interpolate an exception into `detail` — that was a real bug, and "surface the error" does not mean "show the user the traceback".
  - **Uploaded documents are not retained.** The PDF and its `.mmd` live in the request's temp dir and are deleted when the job ends; the per-user indexes are the only copy the pod holds (`DEPLOYMENT.md §7`, `ARCHITECTURE.md §5`). Chunk ids are `<basename>::<n>`, so the temp *directory* may be random but the *file name* must not be — randomising it turns every re-upload into a duplicate instead of a replacement.
  - **A truncated answer is a server fact too.** The generator hits `KBM_NUM_PREDICT` often (deepseek-math fills any budget), so `routes` reads Ollama's `done_reason` and resumes up to `KBM_MAX_CONTINUATIONS` times, appending `chat.TRUNCATION_MARKER` if it is still cut off. Continuation works by sending the partial answer back as an `AIMessage`; Ollama echoes that prefill back at the head of the stream, which `chat.PrefillEcho` strips — **do not remove it, and do not reintroduce `StrOutputParser` into the chat chain**, which would discard `done_reason` and make truncation invisible again.
  - **The continuation loop and the tool loops are one loop with three arms.** `routes` generates, then either the answer ended, or it was cut off at `KBM_NUM_PREDICT` (continuation), or it ends in a closed ` ```python ` block (TIR round), or it came back with native `tool_calls` (agent round). The last two are mutually exclusive by `kbm/config.py`, so only ever two arms are live at once.
  - ⚠️ **A native tool call very often arrives with EMPTY content** — measured on qwen2:7b, two of three probe questions produced zero text beside the call. So the loop's stop condition is `if echo.mismatch or (not produced and not calls)`; without `and not calls` it breaks *before* the tool arm and the student gets `NO_ANSWER_TEXT`. Silent, model-dependent, and it would look like the model failing rather than the server discarding its request. Related: `done_reason` is `"stop"` for a tool call exactly as for EOS, and langchain-ollama mints a fresh `uuid4` per parse — so detect a call from `.tool_calls`, and dedupe on `(name, args)`, never on `id`.
  - **Every tool call gets exactly one result.** Refusals, bad arguments, unknown names and budget denials included. A dangling call breaks the chat template's rendering and leaves the model waiting on a number that never comes — the native form of splicing an ` ```output ` block rather than leaving a fence open. Both arms re-enter by *appending* to `generated` and re-prefilling, which is what keeps `LATENCY.md`'s prompt-prefix rule intact. They are budgeted separately (`KBM_MAX_CONTINUATIONS` vs `tir.MAX_TOOL_ROUNDS`) because they mean different things, and the `while True` carries a pass ceiling on top: the loop is driven by model output, and the round-cap notice is spliced **once** — telling a model twice that it is out of calculations is a loop with no exit.
  - **`PrefillEcho` handles two model behaviours, not one.** Resuming works by sending the partial answer back as a trailing `AIMessage`; deepseek replays that prefill byte-for-byte before continuing, and **ChatML models (Qwen) do not replay it at all**. The class distinguishes full echo (strip it) from divergence-at-character-0 (there was no echo — emit everything) from divergence deep in (abandon). Getting this wrong is invisible: the old version treated the Qwen case as a fault and emitted nothing, so every continuation and every tool round silently produced no text. See `ERRORS.md` 2026-08-20.
  - **The student sees the result, not the code.** `chat.CodeFenceFilter` keeps ` ```python ` blocks out of the token stream while leaving them in `generated` — third in the family with `PrefillEcho` and `QuestionEcho`, same contract: **filters what is shown, never what the model is fed back**. A bare ` ``` ` fence passes through, so a quoted matrix survives. The computed result is always shown (`chat.tool_output_marker`), because hiding the arithmetic entirely would make a wrong sandbox answer indistinguishable from a hallucination — the exact failure TIR exists to remove. `KBM_SHOW_TOOL_CODE=1` reveals the code. **In agent mode `CodeFenceFilter` is inert and inverting it would not help** — the code was never in the token stream at all, it arrives in `tool_calls[i]["args"]` — so the same env var needs its own renderer (`chat.tool_code_marker`), or a debugging switch silently stops working on the newer arm. `chat.search_marker` is the search's counterpart: a native call is invisible in a way a TIR block was not, so without it the student watches a still bubble while retrieval runs and then the answer changes direction for no visible reason. Sandbox *errors* follow the `Job.detail`/`Job.diagnostic` rule: the model gets the traceback line, the student gets a sentence.
  - **Answer provenance is a server fact, not a model claim.** `chat.decide_mode` returns `grounded` (retrieval produced a chunk scoring ≥ `KBM_RELEVANCE_FLOOR`) or `general`, and the server *appends* the provenance itself, as one `Sources:` line at the end of a `grounded` answer (`chat.sources_footer`), listing the deduped document names. A `general` answer gets **no footer at all** — the line exists to name documents and there are none to name, and a "Sources: general knowledge" line printed under every ungrounded answer only taught the eye to skip the footer that does name a file. `mode` on the `sources`/`done` frames remains the authoritative provenance for clients. **A mid-answer `search_documents` does not revise `mode`** — it is the decision the calibrated floor made up front, on the question as asked, and a label that means something different on answers where the model happened to search again is not a label. The late finds go to `done.sources` (same floor applied) and are counted in `done.late_sources`; the footer names them, since its own rule is "name documents iff there are documents". `sources` stays a once-only frame. The model is told not to write a source list of its own, and clients render the footer from the token stream — it arrives flagged `server_marker` so a client can keep it out of the history it sends back. Asking deepseek-math to emit that line was measured and it ignores the instruction — it is a solver, not an instruction-follower. This is also what makes faithfulness measurable at all: without the label, a grounded answer and a hallucination are indistinguishable downstream.
  - **An answer that is only the question is not an answer.** Reported from the running app (no documents ingested) and **not reproducible** — see `ERRORS.md`. `chat.QuestionEcho` guards the head of the stream: it holds text back only while that text is still a prefix of the question and drops it only if it proves to be a verbatim copy, so a real answer streams through untouched. It filters what is *shown*, never `generated` — the continuation prefill must stay byte-identical to the model's own output or `PrefillEcho` will not match it. When the model returns nothing at all, the server says so (`chat.NO_ANSWER_TEXT`) rather than rendering an empty bubble with a sources footer under it.
  - **The relevance floor is applied per chunk, not just to the best one.** `chat.select_context` keeps only chunks scoring ≥ `KBM_RELEVANCE_FLOOR`, and `decide_mode` is then just "did anything survive". A real top-5 looks like `0.9956 0.5881 0.0520 0.0089 0.0068` — a top-N cut is a cut, not a claim that all N are relevant, and the three tail chunks used to be pasted into the prompt *and named in the sources footer*. `routes` filters once and lets mode/sources/context/footer all derive from that one list, so the answer cannot cite a chunk the model never saw. Telemetry deliberately logs the **unfiltered** set with scores, so the floor stays re-calibratable from real traffic.
  - **Not a softmax/top-p (nucleus) selection, and that was measured.** Nucleus is *relative*: it drops a chunk for having a better sibling, discarding chunks at 0.79 and 0.77 because one scored 0.99, and it never keeps five even when all five are good. It also cannot abstain at all — five garbage chunks normalise to the same distribution as five excellent ones. An absolute cutoff does both jobs with one number.
  - ⚠️ `KBM_RELEVANCE_FLOOR` is on a **sigmoid (0–1) scale**, not raw logits: `sentence_transformers.CrossEncoder` applies the model's activation and bge-reranker-v2-m3 carries a Sigmoid. Setting it to a logit-like `0.0` makes every score pass and abstention impossible. **Calibrated to 0.15** by `evaluation/calibrate_floor.py` (was `0.01`, which abstained on only 67% of off-topic questions). It is a property of *that reranker's* output scale — re-run the calibration if the reranker changes.
- **app.py** — Gradio 6.17.3 web UI (port 7860), now an **HTTP client of `api/`**, not an importer of the pipeline. Publishes no API of its own: `show_api=False`, `analytics_enabled=False`, and `api_name=False` on every event binding, so the page cannot be used as a callable backend. Uploading a file *is* the ingest trigger (`upload_box.upload`, not `.change` — the handler clears the box on failure, and `.change` would re-fire on that programmatic clear); there is no ingest button, and a failed upload asks the user to upload again. Kept because a working UI on the real API proves the API is complete before any TypeScript exists; delete it when the TS frontend lands rather than porting it. Keeps a separate "clean" conversation history that it sends back as context, distinct from the display history: token frames flagged `server_marker` (the sources footer, the truncation notice) are shown to the student but kept out of it, so the model is never handed a transcript in which it appears to have written the server's words.
- **kbm/telemetry.py** — append-only JSONL event log (`$DATA_DIR/telemetry/events.jsonl`): one `query` record per answer (hashed user, mode, retrieved chunk ids/scores, per-stage timings) plus `feedback` records keyed by `event_id`. Exists to be *already collecting* by the time it's needed: logged questions are the real query distribution that `EVALUATION.md §8` names as the gap synthetic gold sets cannot close, and thumbs-up (question, chunk) pairs are the contrastive data for an embedding fine-tune (`EVALUATION.md §10.9`). Never let a telemetry failure break a query.
- **ops/idle_stop.py** — watchdog that stops the pod after `KBM_IDLE_STOP_MINUTES` without a `/chat`. This is the entire cost model: on-demand ~$20/mo vs ~$115/mo always-on. Defers while an ingest job is active.
- **evaluation/** — the whole eval harness lives here (scripts, gold set, and a `results/` subfolder for run outputs). The scripts add the parent dir to `sys.path` and use paths relative to `knowledge-base-math/`, so **run them from `knowledge-base-math/`** (e.g. `python evaluation/eval.py …`). Only `evaluation/goldset.jsonl` and the scripts are tracked; `evaluation/results/`, `goldset.raw.jsonl`, and `goldset_review.md` are gitignored.
- **evaluation/make_evalset.py** — builds `evaluation/goldset.jsonl` (question → gold `chunk_id`) by sampling chunks (biased toward math-bearing ones) and having an *instruct* model (`qwen2:7b`, **not** deepseek-math, which is a solver) write the question each chunk answers. Output is a **draft**: questions that parrot chunk wording flatter BM25 and must be rewritten by hand.
- **evaluation/eval.py** — runs the gold set against retrieval configs (`bm25`, `dense`, `hybrid`, `hybrid+rerank`, pool variants) and reports recall@1/@5, **recall@pool**, MRR, nDCG@5, per-stage latency, peak VRAM, and optionally LLM-judged answer quality (`--answers`); writes to `evaluation/results/`. **recall@pool** is the key diagnostic: the reranker can only reorder what BM25/dense already found, so if the gold chunk isn't in the pool the miss is upstream (extraction/chunking), not the reranker's fault.
  - `--match` selects how a retrieval counts as the gold hit: `id` (exact chunk id, same-chunking only) or `overlap` (default; token-containment ≥0.70 against the gold `chunk_text`, so one frozen gold set scores any chunking). `--embed-model`/`--normalize-latex` must match how the target index was built.
- **evaluation/embed_chunk_sweep.py** — the chunking×embedding sweep: builds 9 indexes (3 chunkers × {bge-small, bge-m3, bge-m3+pylatexenc}) from the gold set's source doc into `sweep_<chunk>_<embed>` users, evals each at dense-only + hybrid+rerank via overlap matching, and writes a quality+latency table to `evaluation/results/sweep_results.json`. This is how the "same embedder for LaTeX and prose?" question is decided by measurement.
- **evaluation/self_consistency.py** — does majority voting over k sampled answers beat one greedy answer? Runs **closed-book — no retrieval**, because the subject is the generator's reasoning stability and routing it through retrieval would make a wrong answer un-attributable. Two tiers, and the distinction is the point: `--baseline` (default, `reasoning_set_college.jsonl`, 30 college-level questions) is **the tier that decides model choice**, because a benchmark only discriminates near the incumbent's ~50% mark — deepseek scores 0.85 on the easy tier, where every candidate model would tie inside the noise; `--easy` (`reasoning_set_easy.jsonl`, 20 grade-school questions) is a **regression tripwire** for changes that win on hard questions while breaking basic arithmetic, never a quality score. Draws N samples per question **once** and estimates accuracy at k=1/5/10 by resampling that pool, so every k is scored on identical outputs and k=1 isn't a single-sample coin flip; greedy (temperature 0) is scored separately as the baseline that actually ships. Answers are normalized to numbers before voting — including π/e and LaTeX fractions — so `\pi/2` and `1.5708` are one vote, not two. The output that decides the question is the ERROR STRUCTURE block, not the accuracy table: **BEYOND VOTING'S REACH** counts questions the model is stably wrong about *or* never gets right, and that count is the ceiling sampling can never move. `--report-only` re-scores a saved run without regenerating. See `EVALUATION.md §11`.
- **evaluation/verify_reasoning_set.py** — recomputes every gold answer in both tiers with sympy, from an independent formulation that never reads the JSONL, and exits non-zero on a mismatch or a question with no verification. A wrong answer key marks a *right* model wrong and silently corrupts accuracy, the self-consistency delta, and any model bake-off — it already caught a bad determinant in the first draft of the college set. **Edit a question, edit its verification.** Run it before trusting any generator number.
- **evaluation/eval.sh** — pod runner that wraps the GPU eval: CUDA check → data check → **prefetch all models before any testing** → the sweep, with an optional `--answers` run. See `SETUP.md § GPU eval run`.
- **evaluation/calibrate_floor.py** — sets `KBM_RELEVANCE_FLOOR` from data, two ways. `--corpus-check` runs the real pipeline against a real user index with on-topic (gold set) and deliberately-absent questions, which is the deployment-shaped bound. The default mode scores all 34,813 human-graded pairs of **ARQMath-1** (`hcju/mseqa`, from MIRB, CC-BY-4.0) with the shipping reranker and sweeps the floor for abstention. The external set exists because calibrating a threshold needs **negatives**, and `goldset.jsonl` has none — every row is a question generated *from* its gold chunk, so its positives are vocabulary-matched by construction and would drag the floor upward. ⚠️ That run also measured **pairwise AUC 0.60** for bge-reranker-v2-m3 on human relevance grades, corroborating MIRB's finding that it degrades math retrieval — our final ranking *and* our abstention gate both depend on that model.
- **evaluation/EVALUATION.md** — the evaluation protocol: what's measured, why, the gold-set caveats, cost expectations, and how to act on the numbers. **Read before changing retrieval.**
- **ERRORS.md** — a log of failures actually hit, their real causes, and the fixes. Kept because in nearly every case the symptom pointed somewhere other than the cause (a CUDA build that reports "no GPU", a clean merge that breaks every entry point, an upload path that silently triples the index). **Check it before debugging an environment or ingest problem**, and add an entry whenever a bug takes more than a few minutes to diagnose.
- **AGENT.md** — agent mode's decision record: the two tool protocols and why a model gets exactly one, the three tools, the `user`-is-closed-over rule, why provenance did not move — and **why the loop is hand-rolled rather than a LangGraph agent**, with the four conditions that would make migrating worth it. Read it before adding a tool or reaching for a graph framework.
- **ARCHITECTURE.md** — the residency map: which stage runs on the GPU, which on the CPU, what sits on the volume, and what is left on the laptop. Answers the question the other docs assume: the GPU runs neural-network forward passes and nothing else (four models), while BM25, RRF, chunking and **Chroma's HNSW search** are all CPU. Also carries the VRAM budget and the local-footprint measurement. Read it before reasoning about where a change will cost time or memory.
- **LATENCY.md** — where query time actually goes (generation is ~95%, retrieval ~4%), the fixes applied, and the measurements behind them. **Read before editing `SYSTEM_PROMPT` in `app.py`/`query.py`:** the prompt order is load-bearing — static text → history → context → question — because Ollama only reuses the KV cache of a common prompt *prefix*. Putting per-query context before stable content silently re-prefills the whole prompt every turn.
- **prefetch_models.py** — downloads every HuggingFace model the app needs, before anyone uses it. Exists because the three model sets are fetched at wildly different moments: the embedder (~130MB) and reranker (~2.2GB) load at `app.py` *import*, so a cold cache just makes startup look hung — but **Marker/surya (~3-4GB) is built inside `extract_marker()` and therefore does not download until the first PDF upload**, where `handle_upload`'s `except` reports the stall as a generic `Ingestion failed: <e>`. Fetches through the pipeline's own loaders, so it pulls exactly the files that will be used and doubles as a "do these load here?" check. Called by `startup.sh` (stage 4, skippable with `--no-prefetch`) and by `evaluation/eval.sh` with `--skip-marker` — **one prefetch implementation; don't reintroduce an inline copy in a shell script.**
- **test_chat.py** — ingests a fixed test doc for a `test` user and drops into the same interactive CLI loop as `query.py`, for manual end-to-end verification.

Note: retrieval logic used to be duplicated between `query.py` and `app.py`. It is now shared via `kbm/retrieval.py` — **do not reintroduce a second copy.** An `eval.py` that measures a reimplementation of the pipeline rather than the pipeline itself will drift from what ships and quietly start lying.

The same trap caught the index paths: `CHROMA_DIR`/`BM25_DIR` were declared in *both* `kbm/retrieval.py` and `ingest.py`, so the reader and the writer could disagree about where the data lived. They now come from `kbm/config.py` alone. `test_chat.py` had a third copy of the problem — it built its own `HuggingFaceEmbeddings` instead of calling `load_embeddings`, so the smoke test would have exercised a different loader (and different device) than the app it was meant to smoke-test. **When you add a path, a model, or a host, define it once and import it.**

## Model & infra

- LLM: `t1c/deepseek-math-7b-rl:Q4` served via Ollama — the **default**, not a constant. Selected by `KBM_LLM_MODEL`; candidates and the protocol for choosing between them are `EVALUATION.md §12`. The default stays deepseek until that section has numbers in it.
- Embeddings: `BAAI/bge-small-en-v1.5` (HuggingFace, normalized).
- Reranker: `BAAI/bge-reranker-v2-m3` cross-encoder via `sentence_transformers.CrossEncoder` (~2.2GB, downloads to the HF cache on first use — keep the HF cache on `/workspace` on the pod so it survives restarts).
- Eval-only model: `qwen2:7b` (Ollama) — used by `make_evalset.py` as the *instruct* question-writer and by `eval.py` as the LLM-as-judge. Deliberately **not** deepseek-math (a solver, not a writer; and a model must not grade its own output). Only needed when running the eval harness, not the serving pipeline — `ollama pull qwen2:7b`.
- Designed to run on a RunPod GPU pod; everything must survive on `/workspace` (persistent volume) between pod restarts — `OLLAMA_MODELS`, `HF_HOME`, and **`DATA_DIR`**. The first two cost a ~10GB re-download if missed; `DATA_DIR` is the one that loses the family's uploaded documents outright, because the container filesystem is wiped on restart and the indexes default to the current directory.

## Conventions / constraints

- Prioritize free/open-source models and infra when suggesting changes (Ollama, HuggingFace-hosted models, open embedding models). Do not recommend paid APIs (OpenAI, Anthropic) as the generation backbone.
- Math retrieval quality (notation, proofs, formulas) is a primary concern — consider math-aware chunking/embeddings over generic RAG defaults.
- User wants the option to fine-tune models themselves (embedding and/or generation LLM) down the line.
- Multi-user isolation is per-username directory/collection naming, not real auth — keep this in mind before suggesting security-sensitive changes.
- `chroma_db/`, `bm25_indexes/`, PDFs, and extracted `.mmd` files under `docs/raw`/`docs/extracted` are all gitignored (private user document data) — don't try to commit them.
